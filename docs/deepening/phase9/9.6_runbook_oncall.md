## 关键 Runbook 内容示例

### 1. API 可用性告警处理 (`docs/runbooks/alerts/api-availability.md`)

```markdown
# 告警: SLOApiAvailabilityBurnRateCritical / Warning

## 告警含义
API 请求成功率低于 99.9% SLO，Error Budget 正在快速燃尽。
- Critical: 1h 窗口 Burn Rate > 14.4x (1小时内耗尽预算)
- Warning: 6h 窗口 Burn Rate > 6x (6小时内耗尽预算)

## 影响范围
- 所有 API 调用方 (Web UI、策略系统、风控系统、外部集成)
- 交易信号生成、下单执行、持仓查询

## 诊断步骤 (按顺序)

### 1. 确认告警真实性 (1分钟)
- [ ] Grafana SLO 大盘: `quant-slo` → Error Budget Remaining
- [ ] Prometheus: `sum(rate(http_requests_total{status=~"5..",job="quant-api"}[5m]))`
- [ ] 检查是否为部署/发布导致的短暂波动

### 2. 定位故障域 (3分钟)
| 检查项 | 命令/查询 | 预期结果 |
|--------|-----------|----------|
| Pod 状态 | `kubectl get pods -n quant-prod -l app.kubernetes.io/component=api` | 全部 Running |
| 重启次数 | `kubectl get pods -n quant-prod -o jsonpath='{.items[*].status.containerStatuses[*].restartCount}'` | 0 |
| 资源使用 | `kubectl top pods -n quant-prod -l app.kubernetes.io/component=api` | CPU < 80%, Mem < 80% |
| 依赖连通性 | `kubectl exec -it <api-pod> -- curl -f http://postgres:5432` | 连通 |

### 3. 常见根因与处理

#### A. 数据库连接耗尽
**现象**: `pg_stat_activity` 显示连接数接近上限
```sql
SELECT count(*) FROM pg_stat_activity WHERE state = 'active';
```
**处理**:
1. 检查连接池配置: `quant.config.database.pool_size`
2. 临时增大: `kubectl patch configmap quant-config -n quant-prod -p '{"data":{"config.yaml":"database.pool_size: 50"}}'`
3. 重启 API Pod 释放连接: `kubectl rollout restart deployment quant-api -n quant-prod`

#### B. Redis 连接/内存问题
**现象**: Redis `used_memory` > 80% 或连接数异常
```bash
kubectl exec -it redis-master-0 -n quant-prod -- redis-cli INFO memory
```
**处理**:
1. 清理过期键: `redis-cli FLUSHALL ASYNC` (谨慎)
2. 增加 maxmemory: 修改 `values-prod.yaml` 中 `redis.master.maxmemory`

#### C. 下游服务超时导致级联失败
**现象**: API 返回 504/502，日志显示 `timeout` 关键词
**处理**:
1. 检查下游: Dagster、MinIO、因子计算服务
2. 调整超时配置: `quant.config.http.timeout`
3. 启用熔断: 确认风控熔断器状态

#### D. 代码部署问题
**现象**: 近期有部署，错误率突增
**处理**:
1. 立即回滚: `helm rollback quant -n quant-prod`
2. 或切换蓝绿: `kubectl patch ingress quant -n quant-prod -p '{"spec":{"rules":[{"http":{"paths":[{"backend":{"service":{"name":"quant-api"}}}]}}]}}'`

### 4. 升级路径
| 时间 | 动作 | 责任人 |
|------|------|--------|
| 0-5min | On-call 自行诊断、尝试常见处理 | Primary On-call |
| 5-15min | 无法解决 → 呼叫 Secondary On-call | Primary → Secondary |
| 15-30min | 仍无法解决 → 呼叫 Team Lead + 架构师 | Secondary → Lead |
| 30min+ | 启动重大事故响应流程 | Incident Commander |

## 2. 部署/回滚/扩容 SOP (`docs/runbooks/sop/deployment.md`)

```markdown
# SOP: 部署、回滚、扩容

## 前置条件
- [ ] 通过 CI/CD 流水线所有检查
- [ ] Staging 环境验证通过
- [ ] 生产环境维护窗口内 (或紧急热修)
- [ ] On-call 确认可用

## 标准部署流程 (蓝绿)

### 1. 准备
```bash
# 确认版本
VERSION=v1.2.3
# 确认镜像存在
docker pull ghcr.io/quant/quant:$VERSION
```

### 2. 部署 Green 环境
```bash
helm upgrade --install quant-green helm/quant \
  -f helm/quant/values/values-prod.yaml \
  --namespace quant-green \
  --create-namespace \
  --set quant.image.tag=$VERSION \
  --wait --timeout 15m
```

### 3. 验证 Green
```bash
# 等待 Pod 就绪
kubectl wait --for=condition=ready pod -l app.kubernetes.io/component=api -n quant-green --timeout=180s

# 冒烟测试
curl -f https://quant-green.internal.example.com/health
curl -f https://quant-green.internal.example.com/api/v1/status

# 核心功能测试
python scripts/smoke_test.py --env green
```

### 4. 切换流量 (原子操作)
```bash
# 更新 Ingress 指向 green
kubectl patch ingress quant -n quant-prod \
  --patch '{"spec":{"rules":[{"host":"quant.example.com","http":{"paths":[{"path":"/","pathType":"Prefix","backend":{"service":{"name":"quant-green-api","port":{"number":8521}}}}]}}]}}'

# 观察 5 分钟
sleep 300
```

### 5. 清理 Blue (可选，保留用于快速回滚)
```bash
# 确认无问题后删除 blue
kubectl delete namespace quant-blue
# 或重命名: kubectl rename namespace quant-prod quant-blue
```

## 回滚流程

### 场景 1: Helm 回滚 (最近部署有问题)
```bash
# 查看历史
helm history quant -n quant-prod

# 回滚到指定版本
helm rollback quant 5 -n quant-prod --wait --timeout 5m

# 验证
kubectl wait --for=condition=ready pod -l app.kubernetes.io/component=api -n quant-prod --timeout=60s
```

### 场景 2: 蓝绿回滚 (刚切换流量发现问题)
```bash
# 立即切回 blue
kubectl patch ingress quant -n quant-prod \
  --patch '{"spec":{"rules":[{"host":"quant.example.com","http":{"paths":[{"path":"/","pathType":"Prefix","backend":{"service":{"name":"quant-api","port":{"number":8521}}}}]}}]}}'
```

### 场景 3: 镜像回滚 (镜像有 Bug)
```bash
# 部署旧版本镜像
helm upgrade quant helm/quant \
  -f helm/quant/values/values-prod.yaml \
  --namespace quant-prod \
  --set quant.image.tag=v1.2.2 \
  --wait --timeout 10m
```

## 扩容流程

### HPA 自动扩容 (已配置)
```bash
# 查看 HPA 状态
kubectl get hpa -n quant-prod

# 手动调整副本数 (临时)
kubectl scale deployment quant-api -n quant-prod --replicas=10
# 恢复 HPA 控制
kubectl autoscale deployment quant-api -n quant-prod --min=3 --max=10 --cpu-percent=70
```

### 因子计算 Worker 扩容
```bash
# 扩容 factor-worker
kubectl scale deployment quant-factor-worker -n quant-prod --replicas=10

# 或修改 Helm values
helm upgrade quant helm/quant \
  -f helm/quant/values/values-prod.yaml \
  --set factor.worker.replicaCount=10 \
  --namespace quant-prod
```

### 数据库扩容
```bash
# PostgreSQL 只读副本扩容
helm upgrade postgresql bitnami/postgresql \
  -f helm/quant/values/values-prod.yaml \
  --set postgresql.replication.replicaCount=3 \
  --namespace quant-prod
```

## 部署后检查清单
- [ ] 所有 Pod Running & Ready
- [ ] HPA 正常工作
- [ ] Ingress 流量正常
- [ ] SLO 大盘无异常
- [ ] 关键业务流程冒烟测试通过
- [ ] 通知相关方部署完成
```

## 4. 事后复盘模板 (`docs/runbooks/incidents/template.md`)

```markdown
# 事故复盘报告: INC-YYYYMMDD-XXX

## 基本信息
- **事故编号**: INC-20240115-001
- **标题**: API 可用性下降导致交易信号延迟
- **严重级别**: SEV-1 (Critical)
- **发现时间**: 2024-01-15 14:32 CST
- **解决时间**: 2024-01-15 14:58 CST
- **持续时长**: 26 分钟
- **影响范围**: 全站 API 可用性降至 99.5%，交易信号延迟 30s+
- **报告人**: Alice (On-call Primary)
- **参与人**: Alice, Bob, Carol (Team Lead)

## 时间线
| 时间 | 事件 | 操作人 | 备注 |
|------|------|--------|------|
| 14:32 | Alertmanager 触发 Critical 告警 | 系统 | SLOApiAvailabilityBurnRateCritical |
| 14:33 | Alice 收到 PagerDuty 电话 | Alice | 确认告警 |
| 14:35 | 登录 Grafana 查看 SLO 大盘 | Alice | Error Budget Remaining 12% |
| 14:37 | 检查 Pod 状态、重启次数 | Alice | 发现 quant-api-3 重启 5 次 |
| 14:40 | 查看日志发现 OOM Killer | Alice | `Out of memory: Killed process` |
| 14:42 | 执行扩容: replicas 3→6 | Alice | `kubectl scale deployment quant-api --replicas=6` |
| 14:45 | 观察恢复，Error Budget 回升 | Alice | 可用性恢复至 99.9%+ |
| 14:58 | 确认稳定，关闭告警 | Alice | 事故解决 |

## 根因分析 (5 Whys)
1. **直接原因**: quant-api Pod 内存溢出 (OOM) 被杀死
2. **为什么 OOM?**: 单 Pod 内存限制 2Gi，实际使用峰值 2.1Gi
3. **为什么内存峰值超限?**: 因子计算任务并发过多，缓存未及时释放
4. **为什么并发过多?**: 因子计算调度器未限制单 Worker 并发任务数
5. **根因**: 因子计算调度器缺少内存压力感知和并发限制

## 影响评估
- **用户影响**: 约 50 个活跃策略实例信号延迟 30s，3 个下单失败
- **业务损失**: 估算错失交易机会约 2 笔，潜在收益损失 < 5000 元
- **SLO 影响**: API 可用性 Error Budget 消耗 8% (月度预算)

## 修复措施

### 立即修复 (已完成)
- [x] 扩容 API 副本 3→6 缓解压力
- [x] 调整因子计算调度器并发限制: `max_concurrent_tasks: 2`

### 短期修复 (1 周内)
- [ ] 为因子计算 Worker 添加内存限制和监控
- [ ] 实现因子计算任务队列背压机制
- [ ] 优化因子计算内存使用 (流式处理替代全量加载)

### 长期改进 (1 个月内)
- [ ] 引入 Ray Actor 内存隔离
- [ ] 实现自适应并发控制 (基于内存压力)
- [ ] 完善 SLO 告警分级，避免同类告警风暴

## 经验教训
### 做得好的
- 告警在 1 分钟内触达 On-call
- Runbook 指引清晰，3 分钟内定位到 OOM
- 蓝绿部署架构支持快速扩容

### 需改进
- 缺少内存使用率趋势预警 (只在 OOM 后才触发)
- 因子计算 Worker 无独立监控大盘
- 事后复盘模板缺少量化影响评估字段

| 编号 | 行动项 | 负责人 | 截止日期 | 状态 |
