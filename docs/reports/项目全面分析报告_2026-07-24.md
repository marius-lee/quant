# 项目全面分析报告（2026-07-24）

> 范围：全量代码审查（约 2.9 万行 Python + Flask Web 层），不参考项目内任何文档。
> 所有结论基于代码与生产数据库（task_runs / trades.db / market.db）实况验证。

## 总体判断

项目工程意识超出一般个人项目：分层 pipeline、因子生命周期状态机、walk-forward 回测、
OOS/CPCV/DSR 验证、限价单 OMS、任务编排 DB 状态机齐备。但**会计核算（MTM）与
回测-实盘一致性两个地基存在方向性缺陷**，且生产环境当前有多个功能已静默失效。

## 1. 业务操作流程 vs 业界标准

骨架对齐业界（数据→因子→中性化→组合优化→T+1 执行→归因→因子退役）。6 个关键点不对齐：

1. 会计核算不是 MTM（最致命）：`ExecutionEngine.get_capital` = 现金 + Σ买入成本×股数；
   Web 仪表盘（state_broker）却按收盘价 MTM —— 同一系统两套权益口径并存。
2. 回测与实盘撮合语义分裂（见第 2 节）。
3. 数据复权口径混杂（见 B-08）。
4. 调仓频率名实不符：config 写 `rebalance_freq: weekly` / `rebalance_interval_days: 5`，
   实际每日全量调仓，这两个配置项无人读取。
5. 风控只有告警没有控制：熔断器只写 broker state 无人消费；盘中 ATR 止损已失效（B-01）。
6. OMS 无对账闭环：pending_orders 无部分成交、无废单重报、无日终对账。

商业模型硬约束：本金 ¥5000 + 最低佣金 ¥5 → 单笔 ¥1000 交易单边费用 0.5%，
摩擦成本数学上吃掉大部分 alpha；Nano 层集中持仓方向正确，但决定了策略容量上限。

## 2. 回测 vs 实盘模拟交易

**回测做对的**：walk-forward 逐日推进、T+1 开盘成交、T+1 卖出限制、整手约束、
成本模型、止损+5 日冷却、universe 含退市股（survivorship-free）、因子值物化缓存、
IC 每 60 天滚动重训。

**回测硬伤**：
- 净值曲线成本计价 → Sharpe/MDD/CAGR/Sortino 全部失真。
- `_compute_backtest_metrics` 把指数点位当日收益率 → alpha/beta/IR 垃圾值。
- 执行假设 100% 按开盘价成交 vs 实盘限价单 → 高估成交率 + 动量日逆向选择偏差。
- `capital` / `combine_mode` 参数被 generate_signals 静默忽略 → 无复利、
  warmup→ic_weighted 切换无效。
- 价格口径混杂（B-08）→ 回测不可复现。

**实盘做对的**：DB 任务状态机、防重复触发、限价单状态机、盘中 30s 风控循环、
盘后归因+因子升降级、Phase8 一致性校验模块。

**实盘硬伤**：盘中 ATR 止损失效（B-01）、熔断不落单、归因任务每天崩溃（B-02）、
execute 每天抛 RuntimeError（B-03）、任务超时与 database is locked 频发，
前夜任务链路（daily_data→factor_cache→次日 signals）可靠性是最大系统性风险。

## 3. 技术选型评估

Python+SQLite+Flask+自研 orchestrator+免费数据源对单人小资金快速验证合适，但：

1. SQLite 已到极限（多进程写锁冲突已成生产事故）→ 行情/因子迁 DuckDB+Parquet。
2. 自研编排器+nohup 太脆 → APScheduler + systemd/supervisor，或 cron+单入口 CLI。
3. 数据源 6 源拼凑口径不一 → 落 adj_factor 复权因子表；根治上付费源。
4. factor_cache 物化设计正确但算得慢 → polars/DuckDB 向量化或 numba。
5. 告警通道（telegram/webhook）配置为空 → 接 bark/企业微信 webhook。
6. 工程缺口：71 单测≈3% 覆盖、无端到端回测测试、无 CI、config.yaml 明文 API token。

## 5. 功能盘点

**已实现**：多源行情+增量缺口分析；59+ 因子+物化缓存；因子生命周期状态机
（candidate→active→monitoring→retired/rejected，L1/L2/L3 升降级）；sleeve/composite 合成；
行业/市值/风格中性化；Ledoit-Wolf；资本分层组合构建（Nano/Micro/Small）；
walk-forward 回测；限价单 OMS；盘中风控（数据源坏）；Brinson/因子/换手/滑点归因；
VaR+压力测试+拥挤度；DSR/PBO/CPCV；基准跟踪（口径错）；Flask 仪表盘+SSE+openapi；
任务编排；Phase1-8 评估框架。

**已实现未接线**：HRP、Regime HMM（combine_regime 无人调用）、Optuna、
LightGBM/XGBoost（零调用）、factor_ensemble.pkl、phase7 walk-forward。

**未实现/缺口**：MTM 会计核算；分红送股入账；真实券商接口；分钟级数据与更真实撮合；
告警通道落地；多策略隔离；CI/CD；策略容量/资金曲线管理。

## 6. 架构优化建议

1. 统一执行抽象（最高优先级）：pipeline.execute_signals（回测市价单）与
   scheduler/execute.py + OrderManager（实盘限价单）语义分裂 → 抽象 ExecutionModel 接口。
2. 引入估值层：每晚 post-close 持仓 MTM 写入 daily_equity，绩效/回撤/归因统一读估值表。
3. 数据层切分：行情/因子 → DuckDB/Parquet；账务 SQLite/Postgres；消除跨 7 库应用层 join。
4. scheduler 与 evaluation 职责重叠（attribution vs phase5_monitor）→ 合并。
5. 配置治理：配置项无人读（rebalance_freq）+ 硬编码绕过配置（CIRCUIT_BREAKER_PCT 等）
   → config-key 使用审计。

## 7. 逻辑错误与重构建议

1. 仓位 sizing 用初始本金而非当前权益，与 execute 阶段用当前权益口径矛盾
   → 统一为"当前权益×目标仓位比例"。
2. 两套止损并行不协调（开盘固定 8% + 盘中 ATR）+ 冷却期只在回测实现
   → 收敛为一个 RiskManager 服务，回测实盘共用，实盘加冷却。
3. 监控因子 OOS 窗口太短（train 60d/test 10d）→ 统计功效不足，改用 CPCV+DSR 驱动。
4. `compute_backtest_ic` 权重取 `abs(ic_ir)` → composite 模式负 IC 因子信号反向（latent）。
5. 关键路径裸 `except Exception: pass` 残留 → 错误被吞无法观测。

重构优先级：估值层（MTM）→ 统一执行/风控抽象 → 数据源复权统一 →
因子池/缓存对齐（B-17）→ 配置审计。

## 8. 算法评估

算法栈在个人项目里属超配，不缺"先进"，缺口径正确性和接线：

1. 先修口径（MTM、复权、benchmark 收益率）再谈算法。
2. 把已写好的算法接上：Regime 条件合成、HRP、Optuna。
3. 交易成本感知优化：组合构建引入 Grinold `α - λ·TC` 净收益最大化
   （对 ¥5000 本金+¥5 最低佣金场景，比因子本身更重要）。
4. OOS 统计加固：短窗判定换 CPCV+DSR 驱动。
5. 之后再考虑 ML 合成（LightGBM ranker），必须先过 CPCV/PBO 门禁。

---

**一句话总结**：知道业界标准长什么样、但地基三处（MTM 核算、复权口径、
回测-实盘执行一致性）没打牢。修 P0/P1 的优先级高于一切新功能——
特别是 B-01（盘中止损失效）、B-17（active 因子将被静默丢弃）、
B-06/07/08（绩效评估不可信）。
